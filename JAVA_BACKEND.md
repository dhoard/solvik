# Solvik → standalone Java backend

## Build and run

This compiler targets **Java 25**. The backend is self-contained: a typed Java IR is lowered
from the checked Solvik AST and rendered by a purpose-built Java 25 source renderer. No Java
code-generation library is used.

```bash
./mvnw test
./mvnw -DskipTests package
./solvik run example.sol
./solvik run --keep-sources example.sol
./solvik check example.sol      # compile the whole program, run nothing
```

`./mvnw` automatically downloads its Maven wrapper and Maven distribution on
first execution. Maven also downloads the test dependencies. The shaded
`target/solvik.jar` is a single executable compiler jar, but Solvik programs
generated by the compiler have **no third-party dependencies**.

The launcher retains the original `~/.cache/solvik/` caching behavior for `run`. Set
`SOLVIK_CACHE_DIR` to inspect a separate cache; add `--keep-sources` to retain
`.java` files in the cache after compilation. `check` publishes no entry: it compiles
into a temporary, randomly keyed entry and deletes it, so only `run` reuses cached
artifacts.

## Solvik types and their Java representations

| Solvik type | Java type | Notes |
|---|---|---|
| `Any` | `java.lang.Object` | Dynamic type operations use generated intrinsic methods. |
| `Number` | `java.lang.Number` | Abstraction over the numeric carriers; mixed Big/primitive arithmetic is a type error. |
| `Byte` / `Short` | `java.lang.Byte` / `Short` | Signed 8/16-bit, range-checked at conversion. |
| `Integer` / `Long` | `java.lang.Integer` / `Long` | Signed 32/64-bit; literals default to `Integer`, and `L` selects `Long`. |
| `Float` / `Double` | `java.lang.Float` / `Double` | IEEE 754 binary32/64; literals default to `Double`, and `F`/`D` select `Float`/`Double`. |
| `BigInteger` / `BigDecimal` | `java.math.BigInteger` / `BigDecimal` | Arbitrary precision; their public Java methods are callable directly; `BigDecimal` keeps scale and exact division; `BI`/`BD` select them as literals. |
| `String` | `java.lang.String` | Immutable JDK string; non-null unless written `String?`. |
| `Boolean` | `java.lang.Boolean` | Boxed value; non-null unless written `Boolean?`. |
| `T[N]` | `java.util.List<T>` | Fixed-length, index-mutable array whose length is part of the type; the carrier is unchanged, and the language member `size` reads its length. |
| `T[]` | `java.util.List<T>` | Size-erased array used where the length varies; `size` reads the runtime length. |
| `T?` | the same Java reference carrier as `T` | Java `null` represents Solvik `Null`; no wrapper object is allocated. |
| User `type` | generated `public final class` | No inheritance or interface imposed by Solvik. |
| Native `type … native "…"` | generated final adapter over a Java class | Composition, not inheritance; exported members only. |
| `trait` | generated `public interface` | Bodyless functions are abstract; bodies are Java defaults; concrete types use `implements`. |
| Native `trait … native "…"` | generated interface extending the Java interface | Exact bodyless bindings plus source-provided defaults. |
| `Null` | Java `null` at value sites | The singleton type has one value; a declaration whose type is `Null` uses `Object` as its carrier. |
| `module` `m` | Java package `m` | Types are `m.Type`; functions are `m.Solvik$Functions`. |
| top-level declarations | package `solvik` | `solvik.Solvik$Program` holds `main`, functions, and helpers. |

An array type is written `T[N]` when its length is part of the type and `T[]` when it is
size-erased (`Byte[2]`, `Integer[2][2]`, `Map<String, Byte[]>`, `Integer[]`). Each suffix
applies to the type immediately to its left, and `?` is the nullability suffix at each level,
so `String?[2]` is a non-null array of two nullable strings and `String[2]?` is a nullable
array of two non-null strings. The removed `Array<T>` spelling is rejected with `SOL-P005` and a
message that shows both bracket forms. The carrier is the same for every array: `T[N]` and
`T[]` both lower to `java.util.List<T>`, nested arrays lower to nested `List` carriers, and the
length is enforced by the checker rather than by the carrier. The language member `size` reads the
carrier's length (`List.size()` for both bracket forms); it is the array's only member, it is
immutable, and the call form `x.size()` is rejected. A literal has the form
`ElementType[N] { … }`, where the element type may itself be an array
(`Integer[2][2] { Integer[2] {1, 2}, Integer[2] {3, 4} }`).

An array value is assignable only to an array with the same element type, recursion included; the
array's own `?` is the one widening that is allowed (`T[N]` to `T[N]?`, and `T[N]` to `T[]`). A
wider element type is rejected (`SOL-T001`) because the carrier is a mutable `List`: assigning
`String[2]` to `String?[2]` would let a `Null` be written into the array the first binding still
types as two non-null strings. Element widening is still allowed where the array owns the slot —
a non-null expression in a `String?[N]` literal, or `a[i] = value` on a nullable element type.

Root `module solvik` is reserved for the packaged standard library and generated
code. Program files may not declare or reopen it. Only a `.sol` file packaged as
one of the compiler's own resources receives the loader-owned module-identity
provenance that grants it, and that provenance comes from where the source was
loaded from, never from a filename.

Module blocks are reopened namespaces, not file-owned containers. The loader keeps
all imported declarations and their source positions; the checker resolves members
by full module path across those blocks. The transpiler combines bare functions
from every block/file into one `<package>/Solvik$Functions.java` and emits each
qualified type once. Nested module paths merge recursively; repeated imports do not
duplicate definitions. Module-private helpers are visible across files in that same
module, while outside access still requires `pub`.

Before building type metadata or emitting Java, the checker validates a shared
module/type/function namespace. Module blocks and same-name functions with distinct
parameter signatures may repeat; duplicate signatures, duplicate types, and cross-kind
collisions produce `SOL-T001` with the counterpart's source location. Calls use the
unique most-specific applicable overload and report `SOL-T014` when ambiguous; a nullable and a
non-nullable overload that erase to one Java signature are rejected. Lowering
consumes that same checked logical union for every declaration.

Built-in names belong to that namespace and cannot be redeclared (`SOL-T001`). A type may not take
`Byte`, `Short`, `Integer`, `Long`, `Float`, `Double`, `BigInteger`, `BigDecimal`, `String`,
`Boolean`, `Any`, or `Number`: a written type of that name always means the built-in one, and the
type's generated Java carrier uses the same name. A *top-level* function may not take a built-in
type's name (the conversion wins in call position) or `exit`; a module function and a type member
may, because their calls are qualified or member-selected. `print` and `println` are no longer
built-in names at all: any declaration may use them, and a call resolves only to a user declaration.

## Declarations and mutability

A declaration has three distinct forms: `name := value` infers the type,
`name: Type = value` checks a written type, and `name = value` assigns to an existing mutable
binding. Every local, top-level, and field declaration has an initializer, so a binding's type
is known where it is declared; there is no `var` keyword and no uninitialized slot.

```solvik
total := 0               // immutable Integer
mut count := 0           // assignable again
count = count + 1
label: String = "a"      // explicitly typed
mut title: String? = Null
maybe? := 1              // inferred Integer?
```

`name? := value` asks for the value's type made nullable, and `name? := Null` is `Any?` because
`Null` names no narrower non-null type. `mut` on a type member is required for a write after
construction, exactly as before. A declaration that does not follow this grammar is `SOL-P007`,
the removed `var` keyword and lowercase `null` are `SOL-P006`, and a repeated `?` suffix is
`SOL-P008`.

`T?` and `T` share one Java reference carrier, so the checker — not the carrier — decides where
`Null` may appear. A nullable value must be proven present before member access, indexing,
arithmetic, a condition, or a switch subject; equality, concatenation, and `String(value)` accept it.
The checker narrows a binding after a direct `name != Null` comparison (and in the `else` branch
of `name == Null`, after a guard whose branch always leaves, and for `&&`/`||` combinations), and
it drops that fact when the binding is assigned again. A value assigned or initialized non-null
is present until the next write, so `mut n: Integer? = Null` followed by `n = 1` makes `n + 1`
valid without a further check. No Java-level null check is emitted for a narrowing: the proven
value uses the non-null Java carrier directly. Using a nullable value where a non-null one is
required is `SOL-T015`.

`static` on a type field or function makes the generated member belong to the type
rather than to an instance. It is written first among the modifiers, and it is never
a type-declaration modifier:

```solvik
type Visitors {
    static mut count := 0
    static pub kind := "counter"
    pub func Visitors() { }
    static pub func reset() { count = 0 }
}
```

Static fields become Java `static` fields initialized once, in source order, at class
initialization; `static` functions become Java `static` methods with no `this`.
Static access is emitted through the owning generated class
(`solvik.Visitors.reset()`), while bare names inside the declaring type resolve to
the same Java reference. Instance access to a static member, a type-name access to an
instance member, `self` in a static function, and static members using a generic
type's parameters are Solvik diagnostics (`SOL-T001`/`SOL-T010`).

## Native bindings and `--cp`

A user-authored binding declares the Java class and the members it exports in its
own namespace (not the compiler-owned `solvik` root):

```solvik
module bindings {
    module collections {
        pub type List<T> native "java.util.ArrayList" {
            pub func List()
            pub func add(item: T)
            pub func get(index: Integer) -> T?
            pub func size() -> Integer
        }
    }
}
```

The compiler resolves the Java signatures at compile time (no reflective dispatch),
generates a nominal final adapter in the declaring module's package, and shares one
binding pipeline for packaged standard-library types (for example,
`solvik::collections::List`) and user-authored
`.sol` files. `native "otherName"` selects or renames a Java
overload; a declaration without a return type discards the Java result and is
statement-only.

A `static func` must select a static Java method, and an instance `func` must select
an instance method; a mismatch is `SOL-T013`. This makes static-only JDK classes
usable without a fake instance:

```solvik
module jdk {
    pub type Math native "java.lang.Math" {
        static pub func abs(value: Integer) -> Integer
        static pub func max(a: Integer, b: Integer) -> Integer
        static pub func sqrt(value: Double) -> Double
    }
}
solvik::io::TextWriter(solvik::io::Stdio.stdout()).writeLine((jdk::Math.abs(-3)) .. " " .. (jdk::Math.sqrt(81.0)))
```

A native type that exports only static functions is generated without a delegate
field, constructor, or `toString` override; it retains only the internal
`solvikTypeName()` method used by generated type dispatch. Instance bindings keep
their private delegate and public instance methods exactly as before.

A nullable parameter is accepted by a Java parameter of the same erased type, and a
nullable return is declared by writing `T?`: `String` and `String?` share one Java
carrier, so nullability never changes a generated signature. A Java primitive
parameter cannot receive `Null`, so a declaration that marks it nullable is `SOL-T013`.

### Bundled native declarations

A bodyless `native` member is the second kind of binding. It names no Java class: the compiler owns
a registry (`dev.solvik.compiler.bind.BuiltinBindings`) that maps the exact Solvik signature to one
entrypoint of a generated adapter. Such a declaration is valid only in a type parsed from a
compiler-packaged `.sol` resource; a program file that writes `native` is `SOL-T001`, a missing or
mismatched registry entry is `SOL-T013`, and a supplied body is a parse error.

A type with any native member is *native-backed*. Its generated class is otherwise an ordinary
Solvik class and additionally declares:

```java
private final Object $payload;
private Type(Object $payload) { this.$payload = $payload; }
public static Type $of(Object $payload) { return new Type($payload); }
public Object $payload() { return this.$payload; }
```

A native constructor computes the payload; a native instance method passes `this.$payload` as the
adapter's first argument; a native static method passes none. A `solvik::io::Channel` parameter passes
`channel.$payload()`, and a binding that returns a `solvik::io::Channel` wraps the adapter's result with
`solvik::io::Channel.$of(...)`. Every other value crosses in its language carrier (`List<Byte>` for `Byte[]`,
`String`, `Boolean`, `Integer`). Names contain `$`, so no Solvik declaration can collide with them.

The adapter itself is emitted as `solvik/Solvik$Io.java` only when a binding is lowered. It is
compiler-emitted Java using the JDK and the program's generated `$solvikException`; it is not a
runtime JAR, and its `$` name is not a Solvik identifier. It implements the standard handles,
synchronized `solvik::io::Stdio` bindings, the duplex in-memory channel, strict UTF-8 read/write, CR/LF/CRLF
line recognition, flush-on-write, reader/writer close that never closes the borrowed channel, and
the `solvik::io::IoError`-coded `Exception` failures documented in `LANGUAGE.md` §11.6.

The filesystem additions are five more entries in the same registry: `solvik::io::File.openReadChannel`,
`openWriteChannel`, and `openAppendChannel` return an owned single-direction channel through
`PAYLOAD_RESULT`; `solvik::io::File.exists` and `solvik::io::File.delete` return `Boolean`. They call
`Solvik$Io.openFileRead/openFileWrite/openFileAppend/fileExists/fileDelete`, which use
`FileInputStream`, `FileOutputStream`, and `java.nio.file.Files`. An invalid path becomes
`solvik::io::IoError.InvalidArgument`; an I/O failure becomes `solvik::io::IoError.Io`. `solvik::io::ByteReader` and `solvik::io::ByteWriter` have
no registry entry: their `read`, `write`, `flush`, and `close` are Solvik bodies over `solvik::io::Channel`.
The generated `solvik::io::File` class therefore has no `$payload`; only its type-private open helpers call
the adapter, and every public `solvik::io::File` signature names Solvik types only.

A declared non-null result is checked at the boundary: the call is wrapped in
`Solvik$Program.checked(value)`, which aborts with `SOL-R008` when the Java member
produced `null` anyway. A nullable result is passed through unchanged, and a carrier
that cannot be null (a Java primitive) is not wrapped. Array contents returned by a
binding are not scanned: `LANGUAGE.md` §11.1 permits deferring that validation, and the
current backend performs no per-element check.

A member call on a value of a binding is emitted as a direct call on the adapter only
when the binding **declares** that instance member. An undeclared `type()`,
`toString()`, `equals()`, or `hashCode()` is the `Any` contract and is emitted through
the shared support members (`Solvik$Program.type`, `.hash`, `.equal`, and the render
helper), so the bound Java class never has to offer those names. Declaring
`toString`, `equals`, or `hashCode` on the binding puts that method on the adapter and
selects the Java member; `type()` cannot be declared at all.

In the adapter body, an argument is normally the Solvik value. The one exception is a
declared `equals(other: Any?) -> Boolean` whose Java member takes `Object`: the generated
forwarding hands over `other`'s delegate when `other` is another value of the same
adapter class, so the Java `equals` compares the wrapped Java objects and a binding with
`equals` plus `hashCode` works as a key in the packaged collections. Arguments of other
Solvik types, and every other parameter position, still receive the Solvik value: a
delegate is never stored where the adapter type is expected.

A Solvik module path maps to a Java package, including nested modules
(`shapes::solids` → `shapes.solids`); because Java forbids user classes in `java.*`,
user-authored root `java` maps to `solvik.java`. The packaged standard library uses
`solvik::collections` and `solvik::util`, generating Java packages
`solvik.collections` and `solvik.util`. Program files may not declare root
`solvik`. See `LANGUAGE.md` §10–§12 for the complete surface.

### Standard-library resources: packaged, always loaded, never imported

The standard library is a set of `.sol` resources packaged with the compiler under
`src/main/resources`. `ProgramLoader.packagedResources()` discovers them by
scanning the code source the compiler class was loaded from — a class directory
(`target/classes`) or the JAR — for every entry whose name ends in `.sol`, in
sorted path order:

```text
solvik/collections/List.sol    # solvik::collections::List<T>, java.util.ArrayList
solvik/collections/Map.sol     # solvik::collections::Map<K,V>, java.util.HashMap
solvik/collections/Stack.sol   # solvik::collections::Stack<T>, java.util.Stack
solvik/concurrency/Task.sol    # solvik::concurrency::Task, java.lang.Runnable interface
solvik/concurrency/Thread.sol  # solvik::concurrency::Thread, virtual java.lang.Thread adapter
solvik/util/UUID.sol           # solvik::util::UUID, written in Solvik over Long, System, SecureRandom
```

All of them are loaded into every program, before the entry file and its imports,
and no import names them. Each declares its namespaces with ordinary
`module solvik { module … { } }` blocks; the resource path is a packaging location
and decides nothing about those namespaces. A resource is **declaration-only**: an
import or a top-level statement in one is a `SOL-I003` error, and a listed resource
that cannot be read is a loader error rather than a skipped file.

An import is always a relative file path. `import "solvik::collections::Map"` and
`import "solvik/collections/Map.sol"` look for files with those names and fail with
`SOL-I001`; packaged resources are not reachable as files, and there is no
namespace-import syntax, retired spelling, or allowlist of import names in the
loader. Imports do not bring short names into scope either: callers write
`solvik::collections::Map`.

Provenance and generation:

- `ProgramLoader.Loaded.packagedNames()` records the resource names actually
  loaded. `SolvikCompiler` passes them to `TypeChecker.standardLibraryModules()`,
  an identity-based set of roots parsed from those resources; standalone checker
  entry points trust no roots by default. Every unapproved root `solvik` block is
  rejected (`SOL-T001`), even when an approved block is also present or a source
  name looks like a resource path. Neither filenames nor structurally equal AST
  nodes grant permission to reopen the standard library.
- Because packaged resources precede the entry file, every packaged type is
  generated for every program, and `solvik.Solvik$Program` carries the support
  members the library reaches even when the program uses none of them. Packaged
  source text is part of the compilation-cache key, so a changed library file
  cannot reuse a cached build.
- Native declarations and exported methods use the ordinary
  binding/checking/generation pipeline: `JavaLowerer` emits a Solvik adapter
  with a private delegate, direct calls for declared methods, and the standard
  identity/type-name contract. A native type target must be public and concrete; a
  native trait target must be a public interface. An instance binding with a declared
  constructor needs a matching public Java constructor, while a factory-only binding
  can wrap a returned delegate through its compiler-generated private constructor.

To add another standard-library type, create a declaration-only resource under
`src/main/resources` with one or more native types and let it declare the
namespace it wants (for example `module solvik { module collections { … } }`).
There is no import list, alias table, or registration step: the next compile picks
it up in every program. Extend the structural resource test, the load-order and
provenance tests, and the packaged-JAR test, and update the resource table in
`LANGUAGE.md`. Run a clean build after relocating resources so stale copies cannot
remain in `target/classes` or the packaged JAR.

### Application classpath

```bash
./solvik run --cp "lib/a.jar:lib/b.jar" app.sol   # ';' on Windows
```

`--cp` supplies explicit, ordered JARs (no directories, wildcards, or manifest
`Class-Path`). The same classpath is used to resolve bindings, to compile the
generated Java with `--release 25 -proc:none`, and to run the program; the compiler's
own dependencies are never inherited. JAR content, order, and the JDK version are
part of the cache key. Third-party libraries are supplied by the caller and are not
downloaded.

Literal arrays with complete contents use `Arrays.<T>asList(values...)`; arrays
with unfilled slots use a compiler-generated `array(size, elements)` intrinsic.
These are fixed-size lists, not resizable collections. Their `List` API is an
**implementation detail**, not a new Solvik language feature: the one array member Solvik
exposes is `size`, and it lowers to a direct `List.size()` call. Compared with
native Java arrays they have allocation and dispatch overhead; their bounds
failures are Java `IndexOutOfBoundsException`.

## No runtime class, but generated intrinsics

The transpiler emits `Solvik$Program.java`, one file per user-defined type,
and a Java holder class for each module containing functions. It **does not**
produce `Solvik$Runtime.java`, `Solvik$Type.java`, or link to any Solvik runtime
JAR. Every generated `.java` file can be compiled using `javac` and the JDK
standard library alone.

The packaged library is part of every program's namespace, but only the packaged types a program
mentions are emitted, together with the types those mention. A program that does no I/O therefore
carries neither the I/O type files nor `Solvik$Io.java`, and `Solvik$Program` carries only the
support members the reached declarations use.

A group of static methods and nested exception classes is emitted *inside*
`Solvik$Program` to preserve behavior not provided directly by the JDK:
Solvik-specific conversions, promoted numeric comparison and boxed equality/hash
semantics, dynamic `Any.type()`, recursive array/dynamic-value rendering,
partially initialized arrays, exit status and runtime error codes. The nested classes are
named `$solvikError`, `$solvikExit`, and `$solvikException`: `$` cannot appear in a Solvik identifier, so a user
`type Error` or `type Exit` stays the distinct `solvik.Error`/`solvik.Exit` class instead of
binding to a support type. These members
are **structured Java IR**, not an installed runtime dependency and not injected
source text. Operations are lowered directly to Java where semantics match (see
below). Only the support a program actually reaches is emitted: `JavaLowerer`
records every support member it calls, and `GeneratedIntrinsics` declares each
member (or overload group) as IR. The emitted set is the transitive closure of
the recorded uses, discovered by walking the selected IR for calls to the program
class and references to its nested types, in declaration order. A program with no
conversions, division, dynamic rendering, or exit emits **no** support code at
all. Group granularity is the member name, so every overload of a used name
travels together; an unregistered name fails the compilation instead of emitting
Java that does not compile. Output wrappers and the redundant `toStringOf`
wrapper are not part of the source. The `type()` dispatch names a generic user or
native type with unbounded wildcards (`Box<?>`, `Map<?, ?>`) rather than a raw
type, so a generated program that declares generic types stays warning-free under
`-Xlint:all -Werror`.

## Compile-time lowering

The unified lowering path applies these type-directed rules:

- **Output:** there are no output builtins. `solvik::io::TextWriter.write`, `solvik::io::TextWriter.writeLine`,
  `solvik::io::TextWriter.flush`, and `solvik::io::TextWriter.close` are calls on a generated Solvik class, and the class's
  native members call the generated adapter. `writeLine(text)` is compiled from its `.sol` body,
  `write(text .. TextWriter.EOL)`, so the terminator is the published static value and not
  a literal in the backend. A temporary `solvik::io::TextWriter(solvik::io::Stdio.stdout())` in statement position emits
  `new TextWriter(Stdio.stdout()).writeLine(...)` (the renderer imports `solvik.io.TextWriter` and
  `solvik.io.Stdio`) and needs no flush: the adapter flushes after
  each successful write. No generated statement calls `System.out.print`; a program that wants
  direct JVM output must bind a Java API explicitly.
- **Concatenation:** `..` lowers to one Java string concatenation when both operands render
  directly, and to the `concat` support member otherwise. Java evaluates the operands left to
  right, so side effects keep their source order; the first operand of a multi-operand chain is
  forced to a `String`, because Java's `+` binds to the left.
- **Indexing:** `a[i]` and `a[i] = v` become `list.get(i)` and `list.set(i, v)`.
  The checker already restricts an index to a non-null `Integer`/`Byte`/`Short`
  and rejects an out-of-range literal, so Java's own unboxing is the whole
  conversion: an index that may be `Null` is a compile error (`SOL-T015`), an
  out-of-range index is the JVM bounds failure the CLI reports as `SOL-R004`, and
  no `BigInteger` is allocated per access. There is no `index` intrinsic, and the `SOL-R005`
  "index does not fit an Integer" abort is unreachable and never emitted.
- **Rendering and text conversion:** known scalar types and user objects use
  null-safe JDK text conversion. Inside a concatenation, an operand whose text is
  already the JDK's own (`String`, a boxed scalar, `BigInteger`, a user object)
  is emitted bare: Java renders a reference operand of `+` exactly as Solvik does,
  `null` included. Known decimals use a null-aware Java switch and
  `BigDecimal.toPlainString()`, preserving scale without scientific notation, and
  a `Null` value renders as the literal text `null`. Arrays, `Any`,
  `Number`, and generic values retain recursive/dynamic rendering support. This
  applies to output, `String(value)`, and `.toString()`.
- **Arithmetic and comparisons:** known primitive numeric carriers are unboxed to
  the promoted Java carrier; big numbers use `BigInteger`/`BigDecimal` operations.
  `Objects.requireNonNull` keeps the null check that a boxed carrier needs when the
  checker let a nullable operand through to a native call; the CLI maps native null
  failures to `SOL-R008`. A numeric operand is non-null by the time it is lowered — the
  checker rejects a nullable one — and it already has its promoted carrier, so a literal
  operand and a same-carrier conversion of one emit the literal itself
  (`(-7)`, `2.5d`) instead of a checked unboxing. Division/remainder and other
  explicit conversions retain helpers for Solvik's diagnostic codes and conversion
  grammar.
- **Static members:** a static field is a Java `static` field whose initializer is
  evaluated at class initialization in source order. A static function is a Java
  `static` method; its body has no `this`. Calls and field accesses through a type
  name lower to the generated owner class (`solvik.Owner.member`), including
  module-qualified access and bare names inside the declaring type. Static function
  names that would collide with `Object` instance methods or with a support member of the
  program class use the `$function` suffix; `$` cannot appear in a Solvik identifier, so the
  suffixed name cannot collide with a declaration of its own.
- **Static initializer blocks:** a type has at most one `static { ... }` block; it lowers to a Java
  `static { ... }` member at its source position among static field initializers. The source
  convention places it after all fields and before the first function. Its statements live in a
  private static void method named `$solvikStaticInitN`, and the static block calls that method.
  The indirection is required because javac rejects a static initializer that cannot complete
  normally (for example one containing only `raise`), while a void method may throw freely.
  Compiler-generated regex pattern fields are emitted before every user field and block, so a
  block that uses a regex switch sees initialized patterns. A failure escaping `<clinit>` is
  unwrapped by the CLI from `ExceptionInInitializerError` and classified as the generated exit,
  exception, abort, or Java throwable it actually was.
- **Equality:** `==`/`!=` on statically known primitive numeric carriers use
  null-safe promotion helpers, with separate Float and Double comparisons so
  rounding agrees with arithmetic, so a nullable operand compares without unboxing.
  Arrays and comparisons with `Null` use reference comparisons; other same-carrier
  scalars use boxed equality. Dynamic scalars use
  boxed equality without numeric coercion; user/native objects always use reference
  identity for operators, regardless of their `equals` override. Explicit
  `.equals(...)` uses boxed equality (including BigDecimal scale, NaN and signed
  zero) or the user/native override, never numeric promotion. Arrays keep reference
  equality for explicit `.equals()` too. Distinct user/native types are valid operands
  for the identity operators and necessarily compare unequal.
- **Concatenation:** statically known scalars lower to null-safe Java string
  concatenation. Dynamic or potentially side-effecting rendering retains the
  helper so both operands are evaluated before rendering.
- **Exception handling:** `raise e` is `throw e`, and `try`/`catch`/`finally` lower to
  the Java statement with the same shape. The single `catch` clause catches the nested
  `$solvikException` type, so the abort class, the exit class, and any Java exception
  raised by a native call pass it by without an emitted check. The exception class is
  emitted only when the program raises, catches, or constructs one, and it declares its
  own `getCode()` plus a `toString()` that renders `[code] message`. Its constructor
  rejects a negative code with `SOL-R012`, so a code computed at run time is checked
  once, where the value is built.

For example, `solvik::io::TextWriter(solvik::io::Stdio.stdout()).write("hello")` becomes
`new TextWriter(Stdio.stdout()).write("hello");`, and
`solvik::io::TextWriter(solvik::io::Stdio.stdout()).writeLine("hello")` becomes
`new TextWriter(Stdio.stdout()).writeLine("hello");` with the renderer's imports for `solvik.io.TextWriter`
and `solvik.io.Stdio`. The appended terminator lives in the generated `solvik.io.TextWriter` class as
`static String EOL = TextWriter.lineSeparator();`. No external Solvik runtime is required.

The backend emits primitive Java return types for instance
`equals(other: Any?) -> Boolean` and `hashCode() -> Integer` overrides, as required by
`java.lang.Object`; all other Solvik results retain their usual boxed carriers. The body
sees the parameter as the checked peer, so its `Null` case has already returned `false`.
At the start of a user-defined equality override, lowering emits an `instanceof`
guard that returns `false` for null or another generated class, followed by a cast to
the enclosing type. Body references to the `Any` parameter use that checked peer, which
also makes same-class private fields and methods available. A generic class tests its
reifiable `Type<?>` and gives the subsequent `Type<T>` cast a local unchecked-warning
suppression. Native declarations continue to use their separate delegate bridge.
Top-level/module functions with those contract names (or `toString`) keep their
boxed returns and use a `$function` Java-name suffix to avoid inherited instance
method collisions; Solvik call sites keep their original names. The checker
validates Object-contract signatures before emission. Unsuffixed numeric array
literals are contextually typed before default Integer range validation, including
negative literals and signed carrier minima. Invalid dimensions, void calls in value
contexts, and non-String append targets are rejected as Solvik diagnostics.

A numeric literal suffix (LANGUAGE.md §4) only changes which Java form the literal
becomes: `B` and `S` emit the narrowing cast the carrier needs (`(byte) 1`,
`(short) 2`), `L`/`F`/`D` emit `1L`, `1f`, `1d`, and `BI`/`BD` emit
`new BigInteger("1")` / `new BigDecimal("1.50")`, so `BigDecimal` scale survives
lowering. The suffix never reaches a `case` label: labels lower to their digits, which
keeps them Java compile-time constants. A suffixed literal is typed by its suffix
before emission and does not adopt an enclosing array's element type.

A cast to a reference type parenthesizes a signed operand, because Java's reference cast takes a
`UnaryExpressionNotPlusMinus` (JLS 15.16): the boxed form of `-1` is `(Object) (-1)`, never
`(Object) -1`, which Java parses as a parenthesized expression followed by a subtraction.

Generated user classes are `final` and implement only the Solvik traits they declare. `pub` and
`mut` are enforced by Solvik's semantic checker. Java public fields that are
not `mut` may remain non-final when they are initialized by constructor code;
Java consumers of the emitted classes are **not** yet protected by Java-level
accessors or final-field enforcement. Thus source-level immutability is enforced
for Solvik code, while Java-level immutability requires additional work. Static
members are ordinary Java static fields and methods; their state lives for the
generated class's lifetime, and a static Solvik field is not emitted Java `final`
even when it is Solvik-immutable.

Trait functions retain an explicit body-presence bit in the checked AST: an absent
body emits an abstract interface method, while even an empty `{ }` emits a Java
`default` method. A default is checked with `self` statically typed as its declaring
trait and owns no state. Concrete methods with the same resolved signature override
it. The checker merges all direct trait contracts before emission; multiple defaults
for one signature are rejected unless the class declares an override. If one default
also satisfies an abstract method from another unrelated trait, the generated class
contains a deterministic forwarding method calling the providing trait's static default
bridge, because Java otherwise requires the class to implement the unrelated abstract
method.
Inherited overload lookup uses each function's declaring module, so a default remains
well typed when its trait and implementation live in different packages.

Inside a concrete instance body, `Trait.method(self, arguments...)` records the selected
default declaration on the checked call. The checker requires `self`, direct implementation,
and a source body on the selected trait overload. Lowering emits
`GeneratedTrait.$default$method$N(receiver, arguments...)`, dropping the source-only receiver
name and naming exactly the overload the checker selected.

Each default body is emitted once, as that static bridge on the trait interface; the public
`default` method delegates to it. The bridge's first parameter is the trait-typed `self`, so
calls inside the body still dispatch virtually to the implementing type, while the bridge
itself is a static, context-free entry point. This removes any dependence on Java's
`Trait.super` rules (which require a direct superinterface and an instance context) and
prevents javac from reselecting an overload when arguments are boxed numbers, `Any`
parameters, or `null`. Explicit default calls and the forwarding method for a shared default
both call the same bridge, so they cannot diverge.

For a native trait, bodyless functions are still matched exactly against public Java
interface methods. A source body is not reflected or invoked by the compiler: it emits
as a default on the generated subinterface. If it overrides an inherited Java signature,
the binding phase validates its parameters and return before generation. Defaults for
`type`, `toString`, `equals`, and `hashCode` are rejected before Java emission.

## Compiler architecture

The backend is one pipeline with a strict boundary between meaning, representation, and text:

```text
Solvik source
  -> Lexer / Parser -> Solvik AST
  -> TypeChecker (authoritative semantics; records resolved types, symbols, and targets)
  -> JavaLowerer (AST + TypeChecker.Result -> typed Java IR)
  -> typed Java IR (immutable declarations, typed expressions, structured statements)
  -> JavaSourceRenderer (IR -> deterministic Java 25 source)
  -> javac --release 25 -> JVM
```

- `TypeChecker` decides every Solvik semantic rule: symbol resolution, types, overloads,
  visibility, mutability, construction, trait selection, and native binding targets. It
  records its decisions per node (`TypeChecker.Result`), and lowering consumes them; it never
  re-runs overload resolution or access checks.
- `JavaLowerer` (`dev.solvik.compiler.transpile.JavaLowerer`) maps those decisions to Java
  representations: carriers, conversions, evaluation-order temporaries, intrinsic selection,
  naming, native adapters, traits, modules, and the program class. It builds Java IR nodes only;
  it never builds source text.
- The typed Java IR (`dev.solvik.compiler.jir`) is immutable records and sealed interfaces:
  `JType` (primitive, array, declared, type variable, wildcard, void), `JExpr` (literals,
  names, field and static access, resolved calls, construction, array creation and access,
  binary, unary, cast, conditional, assignment, `instanceof`), `JStmt` (blocks, declarations,
  branches, loops, switch, return/break/continue, try/catch/finally, throw, `super(...)`), and
  `JDecl`
  (compilation unit, class or interface, field, constructor, method, parameter, annotation).
  Every expression carries its Java type; an array type is an element type plus dimensions; a
  call carries its owner and method rather than only a name. `JavaIrValidator` rejects
  malformed IR before rendering.
- `JavaSourceRenderer` (`dev.solvik.compiler.jir.JavaSourceRenderer`) renders only IR. It owns
  indentation, braces, literal escaping, import selection (single-type imports in deterministic
  order, fully qualified names on collision), and every parenthesis, which it derives from Java
  operator precedence and associativity. It contains no Solvik semantics and does not need the
  Solvik AST.
- `GeneratedIntrinsics` declares the JDK-only support members as structured IR. The lowerer
  records the support members it calls; the emitted set is their transitive closure, discovered
  by walking the IR of the selected declarations. No source text is assembled or injected, and
  an unregistered dependency fails the compile.
- The bundled binding adapter is the one generated file that is not IR: `IoSupport` holds its
  fixed embedded source, and `Transpiler` adds `solvik/Solvik$Io.java` only when the lowerer
  reached a native binding. It is compiler-emitted program code, not a runtime library and not a
  language-semantics decision.
- `Transpiler` orchestrates the stages: lower every reached unit, append the reachable support
  members to the program class, render each file in deterministic order, then add the adapter
  when it is needed.

`jcodemodel` is not used. The renderer is purpose-built so the IR can represent exactly the
Java 25 constructs Solvik emits (patterns, arrow switches, generic method invocation, nested
types) without raw source injection. The compiler's dependencies are the JDK and test-scoped
libraries only.

## Validation

Run `./mvnw verify` with Java 25 for a warning-free compile (`-Xlint:all -Werror`
for main and test sources), unit tests, packaged-JAR integration tests, and the
configured coverage gates. The language-consistency regression suite also
compiles generated Java with `-Xlint:all -Werror` and executes it through the
unified backend with an empty dependency classpath. Generated runtime exceptions
declare stable serialization identifiers, native forwarding omits redundant reference
casts, and a class with an intentionally standalone Solvik `equals` override carries a
local `overrides` suppression; generic checked-peer casts use their own local `unchecked`
suppression. `example.sol` runs end to end
(`./solvik run example.sol`) and exercises static user members plus raw and generic
`Map` (Java `HashMap`), `Stack`, `List` (Java `ArrayList`) from the packaged library,
a static-only `java.lang.Math` binding plus a renamed static and an instance
binding in `include.sol`, exception handling through `raise`, `catch`, and `finally`, and the
standard I/O surface: `solvik::io::Channel`, `solvik::io::Channel.bytes()`, `solvik::io::Stdio`, `solvik::io::TextReader`, `solvik::io::TextWriter`,
`solvik::io::TextWriter.EOL`, in-memory redirection, and a caught `solvik::io::IoError`.

The bundled-binding regressions are `NativeBindingTest` (parser/checker acceptance and rejection,
trusted provenance, registry mismatch), `BundledIoExecutionTest` (channel, reader, writer, `solvik::io::Stdio`,
line terminators, error codes, and reader/writer close semantics), and
`ExampleCorpusTest.generated_java_is_warning_free`, which compiles the emitted adapter under
`-Xlint:all -Werror` with an empty dependency classpath. `GeneratedOutputOptimizationTest` pins
that a program without I/O emits neither `Solvik$Io.java` nor the I/O type files.
`BundledFileExecutionTest` covers `solvik::io::File`, `solvik::io::ByteReader`, and `solvik::io::ByteWriter`: open modes, capabilities,
byte round trips, close/borrow rules, path failures, and the generated public shape.
`StaticInitializerTest` covers the static-context rules and rejection cases;
`StaticInitializerExecutionTest` pins once-only first use, source ordering, private-constructor
initialization, block-local scopes, regex initialization, and the generated `static { ... }`
shape; `MainTest` covers class-initialization failure reporting.
`StaticMemberExecutionTest` compiles and runs static user and native members through
the unified backend.
`EmbeddedBindingsTest` checks each packaged resource's declarations, that they load
first and need no import, that the packaged set is the resource tree, that imports
are file paths, and the declaration-only and missing-resource diagnostics;
`UberJarIT` checks the packaged `.sol` set inside `target/solvik.jar` and runs the
library and user bindings from the standalone JAR. JDK-only programs still
compile with `javac --release 25` and an empty dependency classpath; programs using
third-party bindings compile against exactly the JARs supplied with `--cp`.

`ConcurrencyExecutionTest` verifies the generated Java against an empty
dependency classpath: a generated task implements the Runnable-backed Task interface,
`Thread.start` wraps `startVirtualThread`, both `await` overloads reach `join`, and
state written by `run()` is observed on the original task object after completion.

`DefaultTraitExecutionTest` compiles and runs normal and native trait defaults through
the unified backend, including concrete dispatch, trait-typed dispatch, overloads,
explicit overrides, empty defaults, and the abstract-plus-default forwarding bridge.

`GeneratedOutputOptimizationTest` pins the shape of the emitted Java: no support block for a program that reaches none, only the
reachable support members (plus what they need) for a program that reaches some,
direct Java list operations for indexing, temporaries only for output arguments
that can act, and literals folded into their operators; its behavioral cases
compile and run the generated Java with an empty dependency classpath.
`MainTest` confirms a nullable array index is a compile error (`SOL-T015`) and that a
declared non-null native return that arrives as Java `null` still surfaces as `SOL-R008`.

## Performance

Lowering is a single AST walk into IR, and rendering is a single IR walk into a
`StringBuilder`; neither stage builds intermediate Java source strings or resolves a symbol
table twice. Support members are selected by walking only the IR groups a program reaches.

Measured on this repository (Corretto OpenJDK 25.0.3, `example.sol` with the packaged library;
numbers are indicative and are not CI thresholds):

- Compiler transpile stage only (warm JVM, 5 warm-up runs, 20 measured runs):
  **~10.1 ms per full-corpus transpile**.
- Generated program wall time (10 runs, median; JVM start-up included): **~76.5 ms before**
  the refactor, **~70.5 ms after** (~8% lower). The 208-line program output is identical
  except for its random UUID line, checked by running the pre-refactor generated classes and
  the new generated classes side by side.
- Generated source size for the same corpus: 51 files; **3,560 → 3,996 lines** (single-type
  imports and blank lines between members) and **162,306 → 160,094 bytes** (fully qualified
  names are now imported instead). Both versions compile with `javac --release 25`; the new
  one also compiles under `-Xlint:all -Werror`.

Generated-code rules that matter for the JIT are unchanged: direct field and method access,
primitive arithmetic with explicit unboxing where the checker fixed the carrier, conventional
loops, no reflection, and no interpreter dispatch. Support calls remain static calls the JIT can
inline; a program that reaches no support member carries no support code.
